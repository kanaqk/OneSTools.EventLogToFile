# Менеджер журналов всех баз: Windows x64

Требуется установленный Microsoft.NETCore.App 5.0.17 x64. Распакуйте весь архив
`EventLogExportersManager-win-x64.zip` в отдельную папку, например `C:\LogManager`.

Менеджер читает список зарегистрированных баз из `1CV8Clst.lst` в каждом указанном
каталоге `reg_*`. Для каждой базы он ищет `<каталог базы>/1Cv8Log/1Cv8.lgf` и читает
все `.lgp` этого журнала. Базы без `.lgf` и файлы `.lgx` не обрабатываются.
Это работа с каталогами кластера 1С, а не рекурсивный поиск произвольных папок.

В `appsettings.json` укажите следующий полный пример, заменив пути и часовой пояс:

```json
{
  "Logging": {
    "LogLevel": { "Default": "Information", "Microsoft": "Warning" }
  },
  "Manager": {
    "ClstFolders": [
      {
        "Folder": "C:/Program Files/1cv8/srvinfo/reg_1541",
        "Templates": [ { "Mask": ".*", "Template": "[IBNAME]" } ]
      }
    ]
  },
  "Exporter": {
    "StorageType": 3,
    "Portion": 10000,
    "TimeZone": "Europe/Moscow",
    "WritingMaxDegreeOfParallelism": 1,
    "CollectedFactor": 3,
    "ReadingTimeout": 1,
    "LoadArchive": false,
    "SkipEventsBeforeDate": "0001-01-01T00:00:00"
  },
  "JsonFile": { "Folder": "D:/Logs/1C-All", "ProtectCheckpointFile": true }
}
```

`Manager:ClstFolders` — массив: добавьте ещё элементы для других `reg_*`.
Указывайте каталог, непосредственно содержащий `1CV8Clst.lst`.
`Mask: ".*"` включает все зарегистрированные базы; можно задать регулярное выражение
для выбора части баз. `Template` сохраняйте как `[IBNAME]` в файловом режиме:
он используется для наименований хранилищ ClickHouse/Elasticsearch и не изменяет `IBName`.
`Exporter:LogFolder` для менеджера не требуется: путь определяется отдельно для каждой базы.

Запуск из PowerShell:

```powershell
cd C:\LogManager
.\EventLogExportersManager.exe
```

При первом запуске будут прочитаны имеющиеся события. Затем менеджер продолжит читать
изменения и новые LGP, а изменения списка баз обнаружит по `1CV8Clst.lst`.
Для остановки используйте Ctrl+C. Учётной записи запуска нужны права чтения каталогов
кластера и журналов всех выбранных баз, а также записи выходной папки.

Выходные файлы:

```text
D:/Logs/1C-All/<хеш полного пути базы>/20261013000000.jsonl
D:/Logs/1C-All/<хеш полного пути базы>/20261014000000.jsonl
```

Каждая база имеет свою папку, `.position.json` и `.export.lock`. Одинаковые имена баз
в разных кластерах не приводят к перезаписи файлов. Одна база не должна одновременно
экспортироваться двумя процессами в одну и ту же выходную папку.

В каждую новую JSON-строку менеджер добавляет **`IBName`**, например:

```json
{"Id":1,"FileName":"20261013000000.lgp","Event":"Сеанс.Начало","IBName":"Бухгалтерия"}
```

Это имя регистрации базы в кластере, а не имя базы в СУБД и не шаблон хранилища.
Уже записанные строки не изменяются. Для полного экспорта с именем базы используйте
новую выходную папку; не удаляйте позицию в папке, которую уже читает Filebeat.
`LoadArchive: true` читает архив каждой базы с начала, после чего менеджер остаётся
наблюдать список баз; для непрерывного чтения новых событий используйте `false`.

В существующую конфигурацию Filebeat добавьте вход с маской подкаталогов:

```yaml
filebeat.inputs:
  - type: filestream
    id: ones-all-bases
    enabled: true
    paths:
      - 'D:/Logs/1C-All/*/*.jsonl'
    file_identity.path: ~
    prospector.scanner.fingerprint.enabled: false
    parsers:
      - ndjson:
          target: "ones"
          add_error_key: true
```

Сохраняйте вашу существующую отправку в Logstash. Поле будет доступно там как
`[ones][IBName]` (в Elasticsearch — `ones.IBName`). JSON уже разобран Filebeat.
Полный пример с отправкой в Logstash — `filebeat.example.yml` в ZIP менеджера.
Для менеджера используется идентификация файлов по пути: одинаковые первые строки
журналов разных баз не должны восприниматься как один файл. Не переименовывайте JSONL
при таком способе идентификации. Для первой настройки используйте новый input `ones-all-bases`
с новой папкой менеджера; не меняйте идентификацию у уже работающего входа Filebeat.

## Защита последнего JSONL и удаление средствами Filebeat

На Windows включите в существующем `appsettings.json`:

```json
"JsonFile": {
  "Folder": "D:/Logs/1C-All",
  "ProtectCheckpointFile": true
}
```

Используйте локальный NTFS-том. Учётной записи Manager нужны права изменения
разрешений выходных файлов и папок (владелец или соответствующее разрешение ACL).
Filebeat и Manager могут работать под одной учётной записью. На других ОС эта
настройка завершается явной ошибкой; для работы без NTFS-защиты задайте `false`.

Manager устанавливает явный запрет `Everyone: Delete` на активный JSONL и запрет
`Everyone: Delete subfolders and files` только на папку конкретной базы, без
наследования. Последнее закрывает обход запрета через права родительской папки.
Существующие разрешения чтения, записи и изменения ACL сохраняются. Не выдавайте
Filebeat права обхода ACL и не запускайте инструменты, принудительно сбрасывающие
разрешения. Администратор по-прежнему может вручную изменить ACL.

Порядок перехода: открыть и защитить новый JSONL, записать и сбросить события,
атомарно сохранить `.position.json`, затем снять запрет со старого JSONL.
Последний файл остаётся защищённым после остановки или аварийного завершения.
При сбое до сохранения позиции защищёнными могут остаться два файла: после
проверки checkpoint при следующем запуске Manager снимет лишнюю защиту.
Список установленных запретов хранится в `.jsonl-protection.json`; не удаляйте
этот файл, `.position.json` и `.export.lock`.

Сначала остановите Filebeat, обновите Manager, включите настройку и запустите
Manager, чтобы он защитил текущие файлы. Только после этого включайте удаление
и запускайте Filebeat. Новая версия Manager не требует новой выходной папки или
сброса позиции. Сохраните свои `Folder`, настройки кластера и `LoadArchive: false`.

В существующий `filestream` вход Filebeat добавьте:

```yaml
close.on_state_change.inactive: 5m
delete.enabled: true
delete.grace_period: 10m
```

Параметры находятся на том же уровне, что `paths` и `parsers`. Не меняйте `id`,
идентификацию файлов или registry Filebeat. Пример рассчитан на Filebeat с поддержкой
`delete.enabled`; интеграционный тест использует 9.5.5. Проверьте свою версию и
конфигурацию перед запуском:

```powershell
.\filebeat.exe version
.\filebeat.exe test config -c .\filebeat.yml
```

Filebeat читает защищённый файл, но получает `Access denied` при попытке удаления.
Такие сообщения для последнего файла ожидаемы. После снятия защиты Filebeat
повторит попытки и удалит старый файл. Manager сам JSONL не удаляет.
Источник `.lgp`/`.lgf` не изменяется.

При `output.logstash` подтверждение Filebeat означает приём Logstash, а не запись
в OpenSearch. Перед включением удаления настройте дисковую очередь Logstash
(`queue.type: persisted`, достаточный `queue.max_bytes`). Если требуется сохранность
при аварийном отключении питания, учитывайте параметры checkpoint очереди,
в частности `queue.checkpoint.writes: 1` и его влияние на производительность.
Это не проверка успешной индексации: ошибки output, отброшенные события и DLQ
Logstash необходимо контролировать отдельно.

Отключение `ProtectCheckpointFile` не снимает уже установленные запреты: они
сохраняются намеренно. Для возврата к старой версии или ручной очистки сначала
остановите Filebeat и Manager, затем снимите только указанные выше запреты через
свойства безопасности Windows. Остальные ACL менять не требуется.
